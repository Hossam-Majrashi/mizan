║ APP IDEA                                                             ║
╠══════════════════════════════════════════════════════════════════════╣
║ Compare two videos pixel by pixel and tell the user which one has    ║
║ the best quality.                                                    ║
║                                                                      ║
║ PURPOSE                                                              ║
║ The user often downloads two copies of the same video (from          ║
║ different sources or in different versions) and one of them has      ║
║ better quality. The app analyzes both for real and gives one clear   ║
║ answer: which video has the best quality, or that they are the same  ║
║ quality and frames. Judgment comes from the actual picture (the      ║
║ pixels of the decoded frames), never from the file extension or the  ║
║ file size alone.                                                     ║
║                                                                      ║
║ PRIMARY ACTION                                                       ║
║ Home screen = two large slots (Video A, Video B) and one Compare     ║
║ button. Pick through the system file picker; also drag-and-drop on   ║
║ desktop and web. After picking, show file name, size, duration,      ║
║ resolution, and a thumbnail. Swap and clear buttons. Compare stays   ║
║ disabled until both are chosen. No accounts, no internet, no upload: ║
║ everything runs locally and the files never leave the device.        ║
║                                                                      ║
║ WHAT IS MEASURED (real values only, from the actual files)           ║
║ 1. Pixels: declared resolution and total pixel count, and the        ║
║    effective resolution (the real detail present in the picture).    ║
║    Detect upscaling: a declared 1080p video that is really an        ║
║    upscaled 720p has fewer real pixels than a native 1080p one.      ║
║ 2. Pixel-level picture quality from decoded frames sampled at the    ║
║    same timestamps in both videos (aligned by time and scaled to a   ║
║    common size for comparison only): sharpness and fine detail,      ║
║    compression artifacts (blockiness, banding, mosquito noise),      ║
║    noise, color range and accuracy, and a per-frame pixel difference ║
║    between A and B (such as SSIM and PSNR) after alignment.          ║
║ 3. Frames: frame rate (average, plus variable-frame-rate detection), ║
║    total frame count, genuinely unique frames, duplicated frames     ║
║    (for example 60 fps that is really 30 fps repeated), dropped or   ║
║    missing frames, and duration mismatch between A and B.            ║
║ 4. Technical: video codec and profile, bit depth, chroma             ║
║    subsampling, color space, HDR flag, video bitrate, rotation.      ║
║    Audio codec, bitrate, channels, and sample rate are shown as      ║
║    information and used only to break a tie.                         ║
║ 5. Same content check: are A and B really the same video? Use a      ║
║    perceptual comparison of the sampled frames. If they are          ║
║    different videos, say so clearly, still show the technical        ║
║    comparison, and mark the quality verdict as low confidence.       ║
║                                                                      ║
║ VERDICT                                                              ║
║ - One main answer at the top in large text: "Best quality: <file     ║
║   name>" (A or B), with a confidence level (high, medium, low) and   ║
║   one plain sentence of why, for example "B has real 1920x1080       ║
║   detail; A is an upscaled 1280x720".                                ║
║ - Other results: "Same quality and frames" (only when every measured ║
║   difference is inside the tolerance), and "Mixed" when each file    ║
║   wins in different areas. For Mixed, still name the overall better  ║
║   file by the priority order and list where the other one is ahead.  ║
║ - Never name a winner from metadata alone when the decoded pixels    ║
║   disagree. Be honest that picture quality without the original      ║
║   source is estimated, and let that lower the confidence when the    ║
║   evidence is weak.                                                  ║
║ - Priority order, written in code as a documented and tested module: ║
║   real pixels (effective resolution) and pixel-level picture         ║
║   quality, then real unique frame rate and frame completeness, then  ║
║   bitrate, codec, and bit depth, then audio (tie-break only). File   ║
║   size is information only; when the two are equal, mention which    ║
║   file is smaller.                                                   ║
║ - Result screen: verdict card on top; an A vs B table (value, value, ║
║   winner per row, reason one tap away); a frame viewer showing the   ║
║   same timestamp from A and B side by side or with a slider, with    ║
║   zoom to inspect pixels and next and previous sample navigation;    ║
║   copy and save the report as text and JSON.                         ║
║                                                                      ║
║ SETTINGS                                                             ║
║ Analysis depth (quick, normal, thorough = how many sample timestamps ║
║ and how much is decoded) and tolerance for "same" (strict, normal,   ║
║ lenient), plus language and theme. Every option really changes the   ║
║ analysis.                                                            ║
║                                                                      ║
║ ENGINE AND PERFORMANCE                                               ║
║ - Files can be several GB: never load a whole file into memory; read ║
║   from the path or stream, decode only the sampled frames, run the   ║
║   analysis off the UI thread (isolate or native process) with a      ║
║   progress bar showing the current stage and a Cancel button. Leave  ║
║   no temporary files after finishing or cancelling.                  ║
║ - The probing and decoding engine is the heart of the app. Research  ║
║   at execution time and choose, per platform, a real, maintained,    ║
║   license-compatible solution that reads all common video formats    ║
║   and codecs (H.264, HEVC, VP9, AV1, MPEG-4, ProRes... as each       ║
║   platform allows). FFmpeg-based tools are the likely route; check   ║

║ - Handle: not a video file, corrupt file, no video stream, the same  ║

Universal Implementation Template for Flutter Projects
======================================================

How to use:
Edit only the two boxes above, then send this entire file to the coding agent. Any specific platform, extra language, or special constraint goes inside the idea box.
When the agent finishes: link the project to a GitHub repository and push it, and building, testing, and packaging start automatically (section 15).
This file is an execution order for the coding agent. It does not request an app that asks its users for an app name and idea. The two boxes are inputs for the agent only.


00. Execution contract (non-negotiable)
=======================================

- Do NOT produce an implementation plan, outline, proposal, or list of questions. Implement every line of this file literally and write real files in the workspace.
- Every item here is mandatory unless it says "default" or "when needed". The idea defines the product and may restrict platforms and languages or add requirements; it does not cancel the rules for structure, onboarding, theme, or verification.
- When an ordinary detail is missing: choose a sound solution, record it in one line under "Assumptions" in PROJECT_NOTES.md, and continue. Do not ask and do not request approval. The only exception: if both boxes are empty or define no function at all, ask one single question and stop.
- Forbidden: TODO, empty functions, "the remaining files are similar", fake data shown as real results, buttons or settings with no function, and claiming verification that did not happen.
- If a feature needs an unavailable key or service: implement what you can, prepare the correct integration and a separate configuration with an example, and state the exact missing requirement. Never fabricate a result.
- What your environment cannot do (building iOS and macOS on Linux, a missing packaging tool...): still write the complete configuration and scripts, and record the status honestly as "source ready", "built", "run", or "not verified", with the reason.
- Work to completion in a single run. No progress reports along the way; deliver one final report as defined in section 18.


01. Derive the product from its name and idea
=============================================

You are a Flutter and Dart engineer. Turn the name and idea into a complete, real, runnable application, not a description, plan, or interface mockups.

- The idea is the reference for app behavior. The name serves identity and wording only. If the name is missing and the idea is clear, derive a suitable name.

- Add supporting elements (search, export...) only where they have a clear role in the workflow.
- Accounts, sign-in, payments, ads, analytics, and cloud sync only if the idea asks for them. If AI is part of the idea, define its role, inputs, and result review.
- Default platforms: Windows, Linux, macOS, Android, iOS, and Web, with Flatpak as a Linux distribution format.
- If the idea names a platform or a subset, honor that scope exclusively and remove what does not belong. Example: desktop-only app = no screens/mobile, no screens/web, and no Android, iOS, or Web targets. If the function depends on a specific operating system, choose suitable targets and document why.
- Default languages: Arabic and English, plus any language the idea mentions.

03. Google Play acceptance on first review (when Android is targeted)
=====================================================================

Explicit goal: the app is accepted on the first review. Acceptance comes from an app that works and is honest about what it does, not from a good-looking one.

- The core feature really works on a real device, from first launch to result. Test this full path before polishing details. A beautiful app that does not do what it promises gets rejected.
- Choose the correct tools and packages for the app's purpose, and confirm they support Android and the formats and cases the idea actually needs.
- No sample content, placeholder text, dead buttons, or "coming soon" screens. Neither the app nor its store listing claims a feature that does not exist.
- Request the fewest permissions, only at the moment the feature is used, with a translated explanation. Prefer system pickers (file and photo pickers) over broad storage permissions.
- Avoid restricted permissions (MANAGE_EXTERNAL_STORAGE, QUERY_ALL_PACKAGES, REQUEST_INSTALL_PACKAGES, SYSTEM_ALERT_WINDOW, SMS, call log, accessibility, background location) unless the idea requires them; if it does, document the justification and the required declaration in PLAY_NOTES.md.
- Do not put INTERNET or anything else in the main AndroidManifest unless it is used. No cleartext HTTP.
- No ads, analytics, or third-party SDKs unless the idea asks for them.
- If the app collects personal data, needs keys, or uses the network in ways that touch the user: write an honest PRIVACY_POLICY.md in Arabic and English and show its link or text inside Settings.
- At implementation time, check the official documentation for the current minimum targetSdk and the current Google Play requirements for native libraries (including 16 KB alignment), and apply them.
- Production package: a signed AAB. Signing through key.properties, excluded from the repository in .gitignore, with a key.properties.example and the keystore generation command in BUILD_NOTES.md.
- Write PLAY_NOTES.md: short and long store descriptions in Arabic and English (honest), permissions with the reason for each, suggested Data safety answers, content-rating notes, and the list of required screenshots.
- Do not copy another app's name, logo, or identity.
- No crash at startup, when a permission is denied, or when the network drops.

  .pkg.tar.zst
  .tar.gz

15. GitHub Actions: automated build, test, and packaging
=======================================================

Goal: as soon as the project is linked to a GitHub repository and pushed, every targeted platform is built and tested and every package is produced automatically on 64-bit and ARM processors, with no manual setup. Create .github/workflows/build.yml (one file with independent jobs).

Triggers (on): push to the main branch, pull_request, a release tag v*, and workflow_dispatch for manual runs.

Jobs. Create only those for targeted platforms (desktop-only app = no android, ios, or web jobs):

1. verify (Linux x64): install stable Flutter, flutter pub get, localization generation, dart format --set-exit-if-changed, flutter analyze, tool/check_rules.sh, flutter test. All build jobs depend on it (needs).
2. linux: a matrix of x64 and arm64 on native Linux runners for each architecture (no emulation).
   - Install Flutter's Linux prerequisites and the system libraries the project's native dependencies need.
   - Build on the oldest still-supported hosted Linux runner for wider glibc compatibility across distributions.
   - flutter build linux --release, then run build_linux.sh (rpm, deb, pkg.tar.zst, tar.gz, AppImage) and flatpak_linux.sh for each architecture.
   - Any tool missing on the runner (makepkg, rpmbuild...) is provided through a container or a suitable package. If a format is impossible on some architecture, write the reason in BUILD_NOTES.md and mark it "not produced" in the summary; silent skipping or producing a fake file is forbidden.
   - Validate every package before uploading (dpkg-deb --info, rpm -qp, tar -tf, extracting the AppImage).
   - Smoke run: launch the built app under xvfb for a few seconds and confirm it is still running without crashing.
3. windows: x64 and arm64 (a native ARM runner, or a cross-build if the current Flutter support matrix allows it). For each architecture: a portable zip (-portable) and two installers: an .msi (WiX or equivalent) and a -setup.exe (Inno Setup, which supports arm64; install it on the runner if missing), via build_windows.ps1. A Flutter app on Windows cannot run as a single standalone exe (it needs flutter_windows.dll and the data folder), so distribution is either an installer or a zip. Smoke run: launch the program and confirm it is alive after a few seconds.
4. macos: an Apple Silicon runner. Flutter release builds come out Universal (arm64 and x86_64): verify with lipo -archs. Via build_macos.sh produce three dmg files: universal (runs on both), x86_64 for Intel Macs, and arm64 for Apple Silicon (M1 and later). The two dedicated ones are derived from the universal build with lipo -thin on every Mach-O file inside the bundle, then re-signed ad hoc (codesign --force --deep -s -), and each dmg is verified with lipo -archs before upload. Smoke run on the Apple Silicon runner, and on an Intel runner too if the current GitHub documentation offers one.
5. android (when targeted): AAB and per-ABI APKs according to the current Flutter support matrix. Signed when signing secrets exist; otherwise produced unsigned with a clear note.
6. ios (when targeted): flutter build ios --release --no-codesign, then an .ipa (a Payload folder inside a zip) for arm64 (iPhone and iPad). Signed when signing secrets exist (certificate and provisioning profile); otherwise produced with an -unsigned name and a note that installing it needs re-signing.
7. web (when targeted): flutter build web --release and a zip archive. No external deployment unless the idea asks for it.
8. release (on a v* tag): downloads all packages, generates SHA256SUMS.txt, and creates a GitHub Release with every file. The contents: write permission belongs to this job alone.
9. summary (if: always()): a table in the run summary: platform / architecture / format / status.

General rules:
- Install Flutter in a way that works on each runner's architecture: a maintained action such as subosito/flutter-action if it supports the architecture, otherwise clone the stable channel from git.
- The version comes from pubspec.yaml, and outputs are uploaded as artifacts with a reasonable retention period.
- File names in the Release are uniform, and the architecture naming is: Linux uses x86_64 and aarch64 (even if the package uses amd64 or arm64 internally), Windows uses x64 and arm64, macOS uses universal, x86_64 (Intel), and arm64 (Apple Silicon), and iOS uses arm64. - Packaging logic lives in the scripts (build_linux.sh, flatpak_linux.sh, build_windows.ps1, build_macos.sh); the workflow calls them and does not duplicate them, so the same thing runs locally and on GitHub. The scripts detect the architecture automatically.
- fail-fast: false so one platform failing does not hide the rest. Default permissions: contents: read, concurrency that cancels the older run on the same branch, timeout-minutes on every job, and caching for Flutter, pub, and Gradle.
- Hosted-runner labels, ARM availability (Linux and Windows), macOS, and their limits and cost in private repositories: check the current GitHub documentation at writing time, not from memory, and record them in BUILD_NOTES.md. Make the ARM jobs switchable with a repository variable ENABLE_ARM (default true) so they do not hang in the queue if unavailable.
- Official actions (actions/*) at the latest major version confirmed from their pages at writing time. Any third-party action is pinned to a full SHA.
- Secrets are optional and the workflow runs without them (unsigned outputs): Android signing (base64 keystore and passwords), macOS signing and notarization, and Windows signing. Document their names and how to add them in BUILD_NOTES.md. Never print secrets in logs. Pull requests from forks have no secrets.
- 32-bit architectures (ARMv7 and x86-32) are not built in CI for desktop because Flutter does not support them there. Likewise Windows x86, Linux riscv64, and FreeBSD: add jobs for them only if the current Flutter support matrix allows it at execution time; otherwise document the lack of support in BUILD_NOTES.md. Android builds what the current matrix supports.
- The agent cannot run Actions from its environment: record the status as "source ready, not run on GitHub" until it actually runs, and never claim the automated build passed. Explain in BUILD_NOTES.md how to trigger it (push, or the Actions tab then Run workflow) and where the packages appear (Artifacts and Releases).

- DESIGN_DECISIONS.md: why the design is what it is and how it adapts.
- BUILD_NOTES.md: builds, packaging, architectures, and what was verified, plus GitHub Actions runners, optional secrets, and how to trigger it.

- AGENTS.md: points to the files above and preserves these rules for future sessions:
  - The verbatim edit-rule sentence for the three screens folders.
  - Shared logic is never copied between screens.
  - UI strings come from ARB, UI colors from the theme, and tool/check_rules.sh runs before any delivery.
  - Chosen technologies and platforms change only for a documented need, with the docs updated.
  - Any change to platforms, packages, or native libraries also updates .github/workflows/build.yml.
  - Limits and missing requirements are stated plainly, with no claim of unverified completion.

17. Verification gates (mandatory before delivery)
==================================================

Run what the environment allows and record the actual result:

- flutter pub get, localization generation, and icon generation.
- dart format, then flutter analyze with zero issues.
- flutter test: tests for the important business logic, the primary flow, and impactful failure cases, plus the ARB key-parity test. Avoid tests that merely repeat the code without verifying behavior.
- Create tool/check_rules.sh and run it; it fails (exit ≠ 0) on any of:
    1. MediaQuery.of(context).size in lib/
    2. flutter_launcher_icons in any file
    3. abstract class or interface inside lib/platform
    4. TODO, FIXME, or UnimplementedError in lib/
    5. Hard-coded colors (Color(0x… or Colors.* except transparent) outside lib/core/theme, unless marked rule-exempt: content-color
    6. A literal string directly inside Text('…') or Text("…") in the UI
    7. A screens/mobile, desktop, or web folder present though the idea does not target it, or targeted and missing
    8. A missing .github/workflows/build.yml
- Validate .github/workflows/build.yml with actionlint if available, otherwise at least parse the YAML, and confirm it matches the targeted platforms and the scripts that exist.
- Verify: Arabic and English, RTL/LTR, both themes, varied screen sizes, long text, text scaling, and persistence of preferences and data after restart.
- Review every interactive element: it is wired to real logic and nothing overflows.
- Build and run what the environment allows, and record the difference between what was built, what was run, and what could not be verified.
- Keep build and documentation files consistent with the final name, idea, and features.
